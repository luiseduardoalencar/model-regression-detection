# Guide — Calibrating the summary judge

**Used in:** Phase 3 (decision 3.3), after the judge (3.2), classifier prompt
v1 and golden edition 1 exist. Repeated (automatically, on the labeled test
set) whenever the judge model or the judge prompt changes.

## 1. Build the calibration set (automatic)

- **60 summaries** generated by classifier prompt v1 on golden cases, spread
  across the 7 categories.
- **40 summaries** generated by a deliberately degraded prompt (for example,
  "resuma de forma vaga" or "acrescente detalhes"), so there are enough bad
  summaries to measure the judge's ability to fail them.
- Stored in `calibration/summaries.json` with: case ID, email, expected summary, generated summary, source
  (natural or degraded). The source is hidden from Luis while he labels.

## 2. Luis labels each summary (manual)

Agent prompt: [`../agent-prompts/judge-calibration-agent.md`](../agent-prompts/judge-calibration-agent.md).
Labels are saved in `calibration/labels.json`.

The agent shows, one at a time: the email, the expected summary and the
generated summary. Luis answers:

| Field | Values |
|---|---|
| `summary_pass` | pass / fail (overall, per the summary guide) |
| `faithful` | yes / no — only facts stated in the email |
| `main_request` | yes / no — states the main request |
| `critique` | Required on fail: one or two sentences a new colleague would understand (Portuguese) |

Rules for the agent: never show the judge's verdict before Luis answers;
report progress ("37 de 100"); if Luis finds a case the summary guide does
not cover, note it — the guide may need a new rule (criteria drift).

## 3. Split (automatic, fixed seed)

Stratified by pass/fail: **15 train** (their critiques become examples in the
judge prompt), **45 dev** (used to adjust the judge prompt), **40 test**
(hidden; run once at the end).

## 4. Metrics

Positive = "pass". From Luis's labels versus the judge's verdicts on the test
set:

| | Judge: pass | Judge: fail |
|---|---|---|
| **Luis: pass** | true positive | false negative (good summary rejected) |
| **Luis: fail** | false positive (bad summary accepted) | true negative |

- **TPR** = true positives / all Luis passes — share of good summaries the
  judge also passes. Target ≥ 0.85.
- **TNR** = true negatives / all Luis fails — share of bad summaries the
  judge also fails. Target ≥ 0.85. Most important for a regression detector.
- **Cohen's kappa** — agreement beyond chance (reported).
- **Flip rate** — run the judge 3 times on the test set; share of verdicts
  that change (reported).
- Raw agreement alone is never used: a judge that passes everything scores
  high agreement when failures are rare.

Worked example: Luis passes 70 and fails 30; the judge passes 63 of Luis's
70 and fails 24 of Luis's 30 → TPR = 63/70 = 0.90, TNR = 24/30 = 0.80,
raw agreement 87 %, kappa ≈ 0.69.

## 5. Iterate on dev, then test once

1. Run the judge on dev; show the disagreements to Luis with the judge's
   evidence.
2. Adjust the judge's `evaluation_steps` (new judge prompt version) — never
   the labels.
3. Repeat until dev looks good. Optional: compare PT and EN judge prompts on
   dev and keep the better one.
4. Run on **test once**. Record TPR, TNR, kappa and flip rate with the judge
   prompt version in `docs/judge-calibration/judge-vN.md`.

## 6. Outcome

The judge is always advisory in this project (decision 3.4, amended): summary
results can raise a `warning` but never block the PR.

- Targets met → summary warnings are trusted as a review signal.
- Targets missed → the report marks summary results as **uncalibrated**;
  iterate on the judge prompt (a new judge prompt version) and re-run the
  test set.
